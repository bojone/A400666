## 1. 分解与共同闭式

注意本题的正确分解是

$$c(15)=123456789101112131415=3\cdot5\cdot p=15p,$$

$$p=8230452606740808761.$$

$`p`$ 为素数，并且

$$p-1=40Q,\qquad Q=205761315168520219.$$

这里的 $`Q`$ 正好等于 $`a(14)`$ 的大素因子 $`p`$。模 5 看末位、模 3 看数字和，得到候选过滤条件

$$k\bmod15\in\\{0,5\\}.$$

在固定位数 $`d`$ 的区间，令

$$q=10^d\bmod p,\qquad A=(1-q)^{-1}\pmod p,\qquad B=-q(1-q)^{-2}\pmod p.$$

与 $`a(14)`$ 相同：

$$c(k)\equiv Uq^k+Ak+B\pmod p,$$

$$U=\left(c(s-1)-A(s-1)-B\right)q^{-(s-1)}\pmod p,$$

其中 $`s=10^{d-1}`$，以上 $`c(s-1)`$ 均在模 $`p`$ 下计算。

若 $`k=hj`$、$`g=q^h`$ 且 $`\mathrm{ord}_p(g)=L`$，写 $`j=x+Lt`$、$`0\le x < L`$，则

$$c(hj)\equiv Uq^{hj}+Ahj+B\equiv D(t-t_*)\pmod p,$$

$$D=AhL,\qquad t_*=\alpha g^x+\beta x+\gamma\pmod p,$$

$$\alpha=-UD^{-1},\qquad \beta=-L^{-1},\qquad \gamma=-BD^{-1}\pmod p.$$

这些逆元公式要求 $`q\ne1\pmod p`$ 且 $`D=AhL\ne0\pmod p`$。所有生产任务都满足这两个条件。

所以每个 $`x`$ 只求一个小整数 $`t_*`$，不再逐个尝试该等差数列中的所有 $`k`$。精确公式和区间端点由 [src/validate15.py](src/validate15.py) 独立交叉检查。

### 2.1 2–17 位：272 线程 AVX-512

[src/cpu15_avx.cpp](src/cpu15_avx.cpp) 一次处理 8 个 64 位轨道值。64×64→128 位乘法用 32 位乘法和进位拼成，Montgomery 模乘也保持 8 路向量形式。每个线程有独立、可恢复的区间，以 100 万个点为块处理并定期保存进度，而不是把所有任务压在单个顺序队列上。

数值自检先用宿主端 128 位计算核对 1,000,000 组标量 Montgomery 模乘，再将 10,000 组八路向量批次（共 80,000 个值）与标量实现对照。另外还检查截至 1000 的直接拼接、100 个较大输入，以及故意构造的 $`k=15`$ 已知命中。`selftest-cpu` 通过共享封装入口运行这些检查，结束后会清除该测试候选。

覆盖审计为每个 `d`、每个 `a` 检查 272 个终点的精确配置；结果总计

$$13,333,333,333,333,331$$

个轨道点，没有更早候选。详见 [cpu_results/audit.txt](cpu_results/audit.txt) 和最终审计。

### 2.2 18 位：直接余数与 CPU/GPU 无缝交接

令 $`k=a+15j`$。生产 CUDA 程序维护

$$z_j=Uq^a g^j,\qquad w_j=A(a+15j)+B,\qquad g=q^{15},$$

逐点计算 $`z_j+w_j\bmod p`$，直接判断是否为零。这里没有用小 $`t`$ 过滤掉尚未枚举的 $`j`$，所以两个剩余类的合法区间均被完整扫描。$`g^Q=-1`$ 的符号结构也是该任务的重要代数性质，但生产判零不依赖一个未经检查的 $`t`$ 上界。

早期 GPU 忙于高位区间，CPU 同时预处理 18 位前缀。共享队列保存的是所有已完成块的连续前缀，而不是“已分配块”的最大位置，因此中断后不会留下空洞。设 `next_work` 为下一个未分配位置，`active_i` 为线程 $`i`$ 当前块的起点，则安全断点为

$$x_{\mathrm{safe}}=\min(next\\_work,active_0,\ldots,active_{271}).$$

空闲线程的 `active_i` 记录为无穷大哨兵。收到停止请求后不再领取新块，所有活动块完成后才写入最终的 `clean_checkpoint=1` 状态。GPU 只在这种干净边界接管后缀。

两类都使用半开区间 $`6666666666666667\le j < 66666666666666667`$，精确交接如下：

| 类别 | CPU 已完成前缀 | GPU 后缀起点 | CPU 点数 |
|---|---|---:|---:|
| $`a=0`$（[断点](cpu_results/d18_a0_shared.state)） | $`[6666666666666667,10852848839666667)`$ | `10852848839666667` | `4186182173000000` |
| $`a=5`$（[断点](cpu_results/d18_a5_shared.state)） | $`[6666666666666667,7700737376666667)`$ | `7700737376666667` | `1034070710000000` |

每个后缀再分给 8 个 GPU 分片。边界审计确认重叠为 0、空洞为 0；另见 [第二类 CPU/GPU 交接证据](results15/cpu18_a5_handoff_complete.audit.txt)。

### 2.3 19 位：四个余类共享指数轨道

这里 $`k=5j`$，$`g=q^5`$ 的阶为

$$L=4Q=823045260674080876.$$

区间内 $`j=x+Lt`$ 只需考虑 $`t\in\\{0,1,2\\}`$。进一步写

$$x=uQ+r,\qquad u\in\\{0,1,2,3\\},\qquad 0\le r < Q.$$

因为 $`\mathrm{ord}_p(g^Q)=4`$，有

$$g^x=g^r(g^Q)^u.$$

每个 $`r`$ 初始化一次 $`z=\alpha g^r`$ 和 $`w=\beta r+\gamma`$，四个 $`u`$ 的余数类共用 $`z`$ 的逐点更新；每类再乘相应的四阶因子并更新线性项。平均约半次 Montgomery 乘法/轨道点，而不是每点一次完整乘法。

$`k=5j`$ 是便于降维的 superset；主机仍检查 $`k\bmod15\in\\{0,5\\}`$，所以额外的模 3 情形不会被误报。完整搜索没有发现 19 位解。

生产期间进行了两次保持覆盖关系的转换：

1. 将串行断点转换为四陪集断点，见 [迁移记录](results15/d19_coset4_migration.txt)。
2. 把剩余工作量重新均分为 15 个任务，使 8 张卡尽量同时结束，见 [均衡清单](results15/d19_balance_jobs.txt) 和 [迁移哈希](results15/d19_balance_migration.txt)。

#### 串行断点到四陪集断点的精确映射

对于新分片 $`v\in\\{0,\ldots,7\\}`$ 和陪集 $`u\in\\{0,1,2,3\\}`$，定义 $`r`$ 的区间和来源串行 GPU：

$$r_{\mathrm{lo}}=\left\lfloor\frac{Qv}{8}\right\rfloor,\qquad r_{\mathrm{hi}}=\left\lfloor\frac{Q(v+1)}8\right\rfloor,\qquad e=2u+\left\lfloor\frac v4\right\rfloor.$$

令 $`N_e`$ 为串行 GPU $`e`$ 原来的 `next_x`，则转换后的断点为

$$n_{v,u}=r_{\mathrm{lo}}+\min\left(r_{\mathrm{hi}}-r_{\mathrm{lo}},\max\left(0,N_e-uQ-r_{\mathrm{lo}}\right)\right).$$

对于该分片中的 $`x=uQ+r`$，新旧表示描述的是完全相同的已完成前缀：

$$r < n_{v,u}\quad\Longleftrightarrow\quad x < N_e.$$

因此两端的截断十分关键：它既保留已完成工作，又不会引入重叠或空洞。[src/validate15_coset4.py](src/validate15_coset4.py) 检查了这个等价关系、总点数、定向边界和 100 组随机断点映射。

#### 覆盖与剪枝的计数方式

对于一个均衡任务 $`[B,E)`$，令 $`\ell_u`$ 为断点保存时陪集 $`u`$ 需要扫描到的位置，并截断到该任务内；令 $`n_u`$ 为保存的 `next_r[u]`。没有已知 19 位候选时，全局指数上界为 $`x_{\lim}=4Q`$；发现 $`k_{\mathrm{best}}`$ 后改为 $`\min(4Q,k_{\mathrm{best}}/5)`$。所有 $`x < x_{\lim}`$ 都必须覆盖，而 $`x\ge x_{\lim}`$ 的部分可以安全地计为已剪枝。

断点中的“已完成或已剪枝”数量以及显示的 `next_x` 为

$$C=\sum_{u=0}^{3}\left((n_u-B)+(E-\ell_u)\right),\qquad N=4(E-B),$$

$$\texttt{next\\_x}=B+(E-B)\left\lfloor\frac CN\right\rfloor.$$

其中 $`n_u-B`$ 是实际扫描的前缀，$`E-\ell_u`$ 是被剪掉的后缀。因此 $`C=N`$、`next_x=E` **并不表示**全部 $`4(E-B)`$ 个点都实际执行了扫描。最终审计将旧前缀和新分段排序求并集，只加入可安全剪枝的尾部，并检查并集没有重叠或遗漏。

均衡的预计总完工时间从 15.707 小时降到 12.704 小时，约节省 3 小时尾部等待；这是当时依据实测速率作出的估计，不冒充独立实测加速比。最终覆盖计数确认

$$\text{covered\\_or\\_pruned}=823045260674080876,$$

没有重复计数或遗漏。若发现更小的 $`k`$，可把相应搜索界降为 $`k/5`$；只剪掉 $`x\ge x_{\lim}`$ 的区域。

### 2.4 20 位：先找上界，再证明没有更小解

20 位区间取 $`h=1`$、$`L=Q`$。因为 $`\mathrm{ord}_p(10^{20})=Q`$，每个 $`x`$ 直接恢复 $`0\le t\le486`$。8 张 GPU 各处理 $`Q/8`$ 个轨道点。

实际调度不是等整个高位区间全部结束后才看低位，而是：先得到 20 位候选，再完成 19、18 位和低位复核；必要时返回完成被提前停止的高位后缀。这可以同时利用 GPU/CPU，并尽早缩小后续搜索范围。最终 20 位完整区间共有三个解，19 位及以下无解。

21 位备用方案取 $`h=5`$、$`L=4Q`$，对应 $`t\le243`$。由于已经找到 20 位答案，该备用阶段没有投入完整搜索。构建备用程序时必须定义 `T_LIMIT=243`，不能沿用 19 位源码默认值 2。

## 3. 让 GPU 热循环更便宜

所有生产版本都使用 $`R=2^{64}`$ 的 Montgomery 模乘。固定乘数存为 $`gR\bmod p`$，轨道值保持普通表示：

$$\mathrm{Mont}(z,gR)=zg\pmod p.$$

线程从任意位置快速幂初始化，所以能够任意切分、续跑和迁移，而不必从区间起点重算。

主要实测改进如下；不同行的基线、区间和测量阶段不同，**不能简单把百分比连乘**：

| 改进 | 实测效果 |
|---|---:|
| 直接模减替代更复杂归约 | +6.809% |
| 符号位判断与余类对齐 | +15.804% |
| 19 位线性项改为负步长 | +1.517% |
| 小余数延迟规范化 | +3.055% |
| 负步长与延迟判定组合，20 位 / 18 位 | +4.821% / +9.176% |
| 18 位奇数固定乘数，空闲基准 | +6.728% |

小余数判定先检查未规范化的和是否落在 $`0`$ 或小正数附近，只有可能命中时才做最终模归约，避免每点都为几乎不会发生的事件付出同样成本。负步长、符号判断等优化均配套边界、随机对照和断点续跑测试，完整数字见 [speed_history.log](results15/speed_history.log)。

### 64 位归约的精确前提

符号运算之所以有效，是因为 $`p < 2^{63}`$ 且 $`2p < R=2^{64}`$。对于 $`0\le a,b < p`$，和 $`s=a+b`$ 满足 $`0\le s < 2p < R`$，所以加法本身不会溢出。在无符号运算中，$`s-p\bmod R`$ 恰在 $`s < p`$ 时设置最高位；把它解释成有符号 64 位整数，就能正确完成条件减法。对于负步长，`a-negative_step` 严格位于 $`-p`$ 和 $`p`$ 之间，因此一次符号判断加一次条件加 $`p`$ 也是精确的。

对于 $`s=z+w`$，延迟的小候选判定等价于

$$\mathrm{small}_T(s)=(s\le T)\ \lor\ \big(((s-p)\bmod R)\le T\big),\qquad 0\le s < 2p < R.$$

第二次减法按无符号数计算。它恰在 $`s\ge p`$ 且 $`s-p\le T`$ 的分支为小值；发生下溢时则太大，不会通过。这里的 $`T`$ 是 kernel 的小候选上界，例如 0、2 或 486。只有判定成功时才需要规范化模余数。部署的直接扫描 kernel 对该判定检查了 100,000 组随机输入和 6,000 组定向边界；18 位自检还核对了 134 个独立计算的实际余数。

Montgomery 实现使用 $`m\equiv-abp^{-1}\pmod R`$。令 $`lo=ab\bmod R`$、$`hi=\lfloor ab/R\rfloor`$、$`mhi=\lfloor mp/R\rfloor`$，利用模 $`R`$ 的消去可得精确的商表达式

$$r=\frac{ab+mp}{R}=hi+mhi+(lo\ne0).$$

最后一项在 `lo==0` 时为 0，否则为 1。这个恒等式是下面奇数乘数特例的基础。

### 奇数固定乘数：删除 `(lo != 0)` 检测

这是 18 位最后一次已部署优化。设轨道值 $`0 < a < p`$，固定乘数取 $`b`$；若 $`b`$ 为偶数，则用同余代表 $`b+p`$。因为 $`p`$ 为奇数，新乘数总是奇数。

Montgomery 约简中，$`R=2^{64}`$ 且乘数为奇数。若低位乘积 $`lo=(ab)\bmod R=0`$，则 $`R\mid ab`$，进而 $`R\mid a`$，与 $`0 < a < p < R`$ 矛盾。因此该轨道上的低位乘积不可能为零， Montgomery 进位恒为 1，可以把

```cuda
r = hi + mhi + (lo != 0);
```

改成

```cuda
r = hi + mhi + 1;
```

初始化仍使用通用 Montgomery 乘法；只有满足非零轨道前提的固定步进使用此特例。该变换先通过 10 万组通用乘积、10 万组奇数固定乘数、独立轨迹和真实 18 位边界检查，再部署。

8 次重复基准的平均吞吐从 `531481500000` 提升到 `567241000000` 点/秒，提升 6.728%。生产断点实测为 `571588252417.3169` 点/秒。证据见 [数值验证](results15/direct_odd_verification.txt)、[基准](results15/direct_odd_benchmark.txt) 和 [部署记录](results15/direct_odd_deployment.txt)。

这些验证记录是按时间保存的现场文件：例如早期文件中的 `production_changed=NO` 或 `benchmark_result_pending=YES` 描述部署前状态，应与后续基准、部署日志一起阅读，不能覆盖后续记录的含义。

## 4. 两种独立余数验证

### 块和法

[src/verify.py](src/verify.py) 对同位数块计算

$$S_0(n)=\sum_{i=0}^{n-1}q^i,\qquad S_1(n)=\sum_{i=1}^{n}iq^{n-i},$$

利用倍增合并

$$S_0(a+b)=q^bS_0(a)+S_0(b),$$

$$S_1(a+b)=q^bS_1(a)+aS_0(b)+S_1(b).$$

整块余数为 $`r_{\mathrm{start}}q^n+(s-1)S_0(n)+S_1(n)`$。它不依赖素数逆元，可直接在完整 $`c(15)`$ 下计算。

### 矩阵法

[src/verify15_matrix.py](src/verify15_matrix.py) 使用另一个递推表示：

$$\begin{pmatrix}r'\\\\k'\\\\1\end{pmatrix}=
\begin{pmatrix}q&1&0\\\\0&1&1\\\\0&0&1\end{pmatrix}
\begin{pmatrix}r\\\\k\\\\1\end{pmatrix}\pmod M.$$

对每个位数区间做矩阵快速幂，得到相同的完整模数余数。其自检还与小整数直接拼接、块和法和 100 组固定种子随机输入交叉比较。

这两个验证器都不使用 GPU 搜索的 $`t_*`$ 公式。最终审计还重新检查各搜索阶段的配置、端点、完成日志和候选，不能只把 `concat_mod(answer, M15)==0` 当成最小性证明。

## 7. 从零完整重跑的正确顺序

**警告：以下是长任务，不是普通测试。** 建议复制本项目，在新的工作目录使用空 `results15/`、`cpu_results/`，保留 `src/` 内的相对软链接结构。先编译，再分别启动：

```bash
cd a15/src

# 终端 1：低位 CPU，272 线程；campaign 只等待，不会替你启动它
./cpu15_avx all

# 终端 2：首轮 20 位 GPU，8 张卡
python3 run15_d20_fast.py

# 终端 3：监控候选，并按结果继续 d19、d18 或备用 d21
python3 campaign15.py
```

协调器只应在专用搜索环境中运行。它的 `stop_phase()` 使用 `pkill -f` 停止命令行匹配的进程，并用 `pgrep -f` 等待其退出，因此同名的无关进程也可能被停止。所附配置假定使用 8 张 GPU 和 272 个 CPU 工作线程。

`campaign15.py` 不会启动首轮 d20 或低位 CPU；如果没有事先启动它们，它会等待。若 d20 没有候选，协调器进入 d21；找到高位候选后运行 d19、d18，并等待低位 CPU。若没有更早候选，它补齐必要的高位后缀。最后还需显式执行：

```bash
python3 audit15_final.py
```

当前附带的完成证据可用于练习断点接续，但不会等价于从零搜索。19 位四陪集转换和重平衡属于运行中的迁移：`prepare15_coset4.py --prepare` 与 `balance15_d19.py --prepare` 都要求相应的旧断点，不能在没有旧状态时伪造迁移清单。全新任务没有清单时使用串行周期扫描；若启用优化路径，必须按上述前置条件生成并审计新清单。

18 位完整任务可直接使用已支持两类 CPU 前缀的 `run15_d18.py`。`transition15_a5.py` 仅用于复现当时从旧协调器切换到新协调器的受控交接，新任务不需要这个历史切换器；它故意断言原始脚本和二进制哈希，不应通过改哈希来绕过安全检查。

更细的分阶段命令见 `run15_d18.py`、`run15_d19.py`、`run15_d20_fast.py`、`run15_d21.py` 的 `command()`；生产编译宏与 Makefile 完全一致。

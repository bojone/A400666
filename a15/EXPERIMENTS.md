# a(15) 加速实验记录

本文区分“已部署到生产”与“做了数值验证但没有部署”。数据来自 [results15/speed_history.log](results15/speed_history.log)，吞吐单位是轨道点/秒，不是原始候选整数/秒。

## 已部署的改进

### 直接模减与余类对齐

直接模减的一次记录为 $`5.449\times10^{11}\to5.820\times10^{11}`$，提升 6.809%。随后利用 $`p < 2^{63}`$，以符号位和余类对齐减少归约与候选筛选开销，达到 $`6.740\times10^{11}`$，相对上一基线提升 15.804%。

这些优化必须配合边界对照：正常余数、接近 $`p`$ 的和、区间端点和强制命中都要一致。后期 d20、d18 新任务也重新验证了已知命中，而不是仅比较空扫描吞吐。

### 负步长与延迟小余数判定

19 位均衡扫描中，把线性项的加法改为等价的负步长，生产均值提升 1.517%。小余数延迟规范化进一步取得 3.055% 的生产均值提升，寄存器数从 32 降到 30。

“负步长”并非对所有区间独立都更快：早期 d20、d18 单独试验分别慢约 0.336% 和 1.071%，因此当时没有部署。之后与延迟判定、代码布局组合，才在 d20、d18 分别取得 4.821%、9.176% 的提升。这里保留了“单项被拒绝、组合后被采用”的完整过程，避免只展示成功实验。

### 19 位四陪集与均衡调度

利用 $`\mathrm{ord}_p(g^Q)=4`$，四个陪集共享幂轨道，平均约半次 Montgomery 乘法/点。四陪集不是简单把任务名称除以四，还需要把原串行断点映射成每个陪集的独立 `next_r[u]`。

均衡阶段将未完成任务重新分为 15 个作业，使 8 张 GPU 的预计完成时间接近。预计总完工时间减少约 3.002 小时。迁移文件保留原断点哈希，最终审计按区间并集统计覆盖或安全剪枝，不将调度优化误当成可以跳过证明的理由。

### 18 位奇数固定乘数

固定 Montgomery 乘数改成奇数同余代表后，轨道非零保证低位乘积非零，进位恒为 1，可以删除 `(lo != 0)`。推导见 [README](README.md#3-让-gpu-热循环更便宜)。

- 对照：8 次均值 `531481500000`。
- 候选：8 次均值 `567241000000`。
- 提升：6.728268058%。
- 生产断点实测：`571588252417.3169`。
- 热循环：32 寄存器、无溢出，原有占用率已经充足。

对应源码为 [experiments 的对照](experiments/search15_direct.cu) 和 [生产奇数乘数版本](src/search15_direct_odd.cu)。基准脚本位于 [experiments/benchmark15_direct_odd.py](experiments/benchmark15_direct_odd.py)，需要当时保留的控制二进制及其哈希，不适合作为新环境的一键通用基准。

### CPU 与 GPU 重叠执行

GPU 搜高位时，272 个 CPU 线程完成低位和部分 18 位前缀。18 位共享 CPU 队列只把连续、已完成的前缀作为可恢复断点。GPU 接管时先等待 CPU 在块边界干净停止，再按同一 `next_x` 划分 8 个后缀。

第二余类交接点的重叠和空洞均为 0。该优化提高的是设备利用率，不能用单个 kernel 的百分比衡量。

## 已验证但未部署的方案

| 方案 | 结果 | 保留原因 |
|---|---|---|
| 无符号 `min` 模归约 | 比延迟判定慢约 4.357% | 有 204,008 组算术对照和 779 组强制余数测试，但性能不合适 |
| 32 位粗过滤 | 无稳定加速；额外命中增加原子操作 | 边界测试通过，但生产 kernel 不变 |
| 合并命中分支 | 慢约 4.7% | 代码分组并未减少实际瓶颈 |
| 跨区间配对共享幂（`pair18`） | 慢约 62.7%；寄存器 32→52 | 配对映射与寄存器开销抵消共享收益，见[原始基准](results15/search15_pair18_benchmark.log) |
| 18 位直接两陪集配对（`direct_pair`） | 第二余类完全落在 19 位区间 | 直接拒绝，未使用忙碌状态基准作决定，见[拒绝审计](results15/direct_pair_rejected.audit.txt) |
| 32 位循环计数 | 热循环指令 276→282 | 寄存器虽 32→28，但当前已满占用，更长热循环没有收益 |

相关源码集中在 `experiments/`：

- `search15_minmod.cu`：无符号最小值归约。
- `search15_lazyfilter.cu`：小余数过滤实验。
- `search15_negstep.cu`、`search15_signed.cu`：步进与符号余类优化。
- `search15_direct.cu`：直接扫描的控制版本。
- `search15_coarse.cu`、`search15_grouped.cu`：粗过滤与合并命中分支实验。
- `search15_pair18.cu`：跨 18、19 位区间的配对共享方案，对应 62.7% 减速记录。
- `search15_direct_pair.cu`：18 位直接两陪集配对，第二余类超出 18 位区间。
- `search15_direct_counter.cu`：32 位循环计数候选。

更多被否定思路的原始参数可在 `speed_history.log` 中查阅。`results15/` 还保留了粗过滤、分支合并和 `pair18` 的原始测试及基准日志。例如粗过滤与分支合并的强制覆盖测试通过，但基准没有提升；这类“数学等价但不更快”的方案没有进入生产路径。

## 性能比较时的注意事项

1. **先正确，后计时。** 每次替换都做数值对照、已知命中和断点恢复检查。
2. **同一区间、同一基线。** 表中的百分比来自不同阶段的基线，不能直接连乘成总加速比。
3. **看总完工时间。** 19 位尾部空载比单卡峰值更重要；CPU/GPU 交接同理。
4. **区分扫描吞吐和有效工作量。** 周期降维后的一点可能代表很多原始整数；四陪集共享还改变每点成本。
5. **保留失败实验。** 没有部署不等于数值公式错误，有时只是寄存器、指令数或任务形态不合适。
6. **历史记录按时间读。** 部署前文件中的 `production_changed=NO` 是现场状态，后续部署文件才记录最终切换。

## 仍可探索的方向

- 更通用的多精度或 Barrett 约简，以摆脱固定 64 位素数限制。
- 自动生成不同阶数下的陪集分解和任务映射，而非针对本例手写四陪集。
- 把覆盖证明导出为更容易独立检查的区间证书格式。
- 在其他 GPU 架构上重新评估寄存器、向量化与块大小，不照搬本机的最优组合。

这些是未来工作，不是本次已经实现或验证的功能。
